# whiteEditor

Редактор сцен для веб-игр на three.js в духе Unity. Личный инструмент и практика автора, не продукт.
Игра создаётся из одного места — из редактора; проект игры живёт в папке `projects/<имя>/`.

## Цели (в порядке важности)

1. **Модель Unity:** GameObject + компоненты, Hierarchy, Inspector с Add Component, окно Project с ассетами,
   префабы. Тяжёлые системы (физика, анимации, частицы, UI игры) — позже и в упрощённом виде.
2. **С инструментом должен хорошо работать ИИ-агент.** Весь проект — читаемые текстовые файлы (JSON, TS),
   которые можно писать руками; редактор подхватывает правки с диска; есть описание формата для агента
   и проверка без браузера. При конфликте с «красотой как в Unity» эта цель важнее.
3. **Просмотр рендера:** свет, туман, день/ночь, эффекты вроде погружения под воду должны быть видны
   прямо во вьюпорте — он рисует тем же three.js и тем же кодом движка, что и игра.

Разработку не привязываем к переносу конкретной игры. Прежняя игра автора (`D:\Projects\office`) —
только пример подхода «модели собраны функциями в коде».

## Как работать

- В чате — по-русски. Комментарии в коде — по-английски, в стиле окружающего кода (4 пробела, двойные
  кавычки, точки с запятой в `src/`; в `vite*.ts` и `tools/` — 2 пробела, одинарные кавычки, без `;`).
- После правок: `npx tsc -b`, `npx eslint .`, `npm run check -- demo`.
- Dev-сервер автор обычно держит запущенным сам на `http://localhost:5173` — второй не поднимать,
  а открыть этот адрес в браузере.
- Перетаскивание (HTML5 drag-and-drop) инструмент браузера настоящей мышью не воспроизводит — проверять
  программными событиями и честно говорить, что мышью не проверено.
- Коммитить только по просьбе.

## Команды

```bash
npm run dev              # редактор
npm run check -- demo    # проверка проекта: сцены, префабы, материалы, типы скриптов (без браузера)
npm run build:game -- demo [сцена]   # сборка игры в projects/demo/build (index.html + game.js)
npx tsc -b               # типы редактора
npx eslint .
```

## Структура

| Путь | Что это |
|---|---|
| `src/engine/` | Ядро без React: формат данных, компоненты, материалы, окружение, сборка three.js-объектов, валидация. Его же импортируют скрипты проектов как `white-engine` |
| `src/editor/core/SceneStore.ts` | Состояние редактора: дерево объектов (источник правды), three.js-объекты по нему, выделение, undo / redo, режим префаба, режим Play (запущенная копия сцены, пауза, вид Scene / Game) |
| `src/editor/core/actions.ts` | Всё, что ходит на диск: проекты, сцены, материалы, префабы, сборка игры, реакция на внешние правки |
| `src/editor/core/project.ts` | Клиент API dev-сервера, загрузка скриптов и ассетов проекта в `Registry` |
| `src/editor/*.tsx` | Панели: `Toolbar`, `Hierarchy`, `Inspector`, `ProjectPanel`, `Welcome`, `ContextMenuHost`; общие части в `ui.tsx` |
| `src/editor/editor.css` | Весь внешний вид редактора (классы, переменные цветов) |
| `src/components/Viewport.tsx` | Вьюпорт: рендер (сцена редактора или запущенная копия), гизмо, выбор, полёт камеры, фокус, сетка, цикл кадров Play, подключение ввода игры |
| `vite-plugin-projects.ts` | Серверная часть: API `/__api/projects/...` (в том числе сборка игры), раздача сборки на `/__game/<имя>/`, слежение за файлами, генерация `AGENTS.md` |
| `tools/agentDocs.ts` | Текст `AGENTS.md` для проектов; таблицы полей строятся из определений движка |
| `tools/check.mjs` | Проверка проекта из командной строки |
| `tools/buildGame.ts`, `tools/build.mjs` | Сборка игры в статические файлы; первый — сама сборка (её же вызывает dev-сервер), второй — команда |
| `src/engine/prefab.ts` | Экземпляры префабов: `expandInstance` (содержимое префаба с применёнными переопределениями), `diffOverride` (чем правленый объект отличается от префаба) |
| `src/engine/look.ts` | Look (стиль рендера): формат ассета, `resolveLook` (наследование через `extends`), `defineEffect`, встроенные эффекты |
| `src/engine/pipeline.ts` | `RenderPipeline`: рисует сцену через Look — поверхности в материалах, уменьшенная картинка, цепочка экранных эффектов, вывод на канвас. Общий для вьюпорта, Play и собранной игры |
| `src/engine/shaderParams.ts` | Как параметры эффекта или поверхности становятся uniform'ами (`uniformNames`, `uniformDeclaration`, `uniformValues`); общий для `pipeline.ts` и `surface.ts` |
| `src/engine/surface.ts` | Слой «поверхность»: `defineSurface`, встроенные поверхности (`vertexSnap`, `toon`, `flat`), класс `Surfaces` — вставляет их в материалы рисуемой сцены и убирает обратно |
| `src/engine/runGame.ts` | `runGame(container, registry, scene)` — вся игра вне редактора: рендерер, `Game`, ввод, цикл кадров; `createRenderer()` — общий с вьюпортом |
| `src/engine/game.ts` | `Game`: запущенная сцена — объекты, окружение, камера сцены, `Runtime`; `start()` / `update(dt)` / `resize()` / `dispose()`. Через него идут и Play в редакторе, и собранная игра |
| `src/engine/input.ts` | `Input`: состояние клавиатуры и мыши для поведений (`self.input`); `attach(canvas)` слушает события браузера |
| `src/engine/runtime.ts` | `Runtime`: запускает поведения (`script`-компоненты) собранной сцены, `start()` / `update(dt)` |
| `projects/demo/` | Тестовый проект: сцены `main`, `underwater`, три материала, префаб `Pillars`, стили `PixelArt`, `PixelArtDark` (расширяет первый), `PS1`, `Sketch` (тушь на бумаге: штриховка и «кипящие» контуры) и `Pico8` (палитра из 16 заданных цветов), скрипты с моделями, поведениями (`spin`, `bob`, `drive`), эффектами (`scanlines`, `wobble`, `hatch`) и поверхностями (`sway`, `boil`) |

## Как устроено

- **Проект** — папка `projects/<имя>/`: `scenes/`, `materials/`, `prefabs/`, `looks/` (JSON), `scripts/` (TS), `assets/`,
  плюс `tsconfig.json`, `AGENTS.md` (генерируется, перезаписывается при запуске сервера) и `CLAUDE.md`
  (создаётся один раз, для заметок автора). Проекты лежат только внутри папки редактора: так у скриптов
  и редактора одна копия three.js.
- **Формат** (версия 3) подробно описан в `projects/demo/AGENTS.md`. Кратко: сцена — дерево объектов;
  объект — контейнер с `position`, `rotation` (градусы), `scale`, `components`, `children`; значения
  по умолчанию и `id` можно не писать. Компоненты: `mesh`, `light`, `camera`, `model`, `script`; не больше
  одного каждого типа, кроме `script` (сколько угодно, но каждое поведение один раз). Настройки сцены —
  `environment` (фон, окружающий свет, туман).
- **Компоненты описаны в `src/engine/components.ts`** (`componentDefs`): поля, функция сборки и особенности.
  Inspector, валидация и `AGENTS.md` строятся из этих определений — новый компонент добавляется там.
- **Поле, нужное не всегда:** у `ParamDef` есть необязательное `when` — `{ kind: ["spot"] }`: поле имеет смысл,
  только пока другие поля того же объекта имеют одно из этих значений. Inspector такие поля прячет
  (`fieldApplies`), `AGENTS.md` пишет условие в таблице; значение в файле хранится в любом случае. Так
  размечены `range`, `angle` и `shadowSize` у света.
- **Материал** — ассет `materials/<имя>.json`; `mesh.material` ссылается по имени. Один three.js-материал
  на ассет, общий для всех мешей (`userData.shared`, при удалении меша не освобождается).
- **Модель из кода** — `defineModel({...})`, экспортированный из любого файла в `scripts/`. Редактор
  импортирует скрипты через Vite; правка файла перезагружает их без перезагрузки страницы
  (событие `white:scripts-changed`).
- **Поведение** — `defineBehavior({ name, params, start, update })` из `scripts/`, вешается компонентом
  `{ "type": "script", "script": "<имя>", "params": {...} }`. three.js-объекта у него нет: `createEntityObject`
  кладёт скрипты в `userData.scripts` группы (`setScripts`), а `Runtime` обходит дерево и запускает их.
- **Особенности компонента описаны в его определении**, а не проверками `type === ...` по коду:
  `create` (нет — компонент ничего не рисует), `source` (содержимое берётся по имени из `scripts/`, его
  параметры лежат в `component.params` — так устроены `model` и `script`), `multiple` (можно несколько на
  объекте). Компонент внутри объекта адресуется ключом `componentKey()`: тип (`"mesh"`) или
  `"script:spin"` для `multiple`. Этим же ключом помечен его three.js-объект (`userData.component`),
  по нему работают методы store (`addComponent`, `removeComponent`, `setComponentField`,
  `setComponentParam`), ключи React и поиск дублей в валидации.
- **Play** (`sceneStore.play()` / `stop()`, кнопка в Toolbar, Ctrl+P): store создаёт `Game` из данных сцены —
  отдельную копию объектов, собранную тем же кодом движка, что и игра. Вьюпорт рисует `sceneStore.viewScene`
  (сцена игры во время Play, иначе сцена редактора); какой камерой — см. «Два вида» ниже. Объекты
  редактора скрипты не трогают. В копии нет сетки и маркеров. Кадры двигает вьюпорт (`sceneStore.tick`).
  В режиме префаба Play недоступен.
- **Правка во время Play** разрешена и видна сразу. Методы store меняют данные сцены и тут же копию:
  transform, имя, active — `game.syncEntity`, компоненты — `game.syncComponent` (вызывается из
  `rebuildComponent`), окружение — `game.setEnvironment`. Параметры скрипта `Runtime` читает прямо из
  данных компонента, поэтому их правка не сбрасывает состояние поведения. Изменения дерева (добавить,
  удалить, перенести объект, префаб ↔ объект) пересобирают копию заново (`restartGame`) — состояние
  поведений при этом сбрасывается. Гизмо в Play переезжает в сцену копии и держит её объект
  (`selectedViewObject`); `syncFromGizmo` пишет в данные только то, что меняет текущий режим гизмо
  (позицию, поворот или масштаб), чтобы не сохранить то, что накрутил скрипт.
- **Два вида в Play, как вкладки Unity:** переключатель Scene / Game во вьюпорте (`sceneStore.playCamera`).
  Play всегда стартует в Game: камера сцены (`Game.camera`: первый активный объект с компонентом `camera`),
  клавиши и мышь идут в игру — выглядит и играется как собранная игра; выбор кликом, гизмо, меню и полёт
  выключены (`sceneStore.gameView`). Scene — камера редактора с выбором и гизмо, чтобы подвинуть что-то на
  ходу. Сцена работает в обоих видах, Hierarchy и Inspector правят её в обоих. Если камеры в сцене нет,
  вида Game нет, Play идёт в Scene.
- **Пауза и шаг** (`sceneStore.paused`, `togglePause()`, `step()`; кнопки в Toolbar, Ctrl+Shift+P и
  Ctrl+Alt+P): на паузе `tick` не двигает игру; шаг ставит паузу и двигает сцену на один кадр (1/60 с).
  Пауза возвращает полный редактор: `sceneStore.gameView` на паузе ложно, поэтому вьюпорт показывает
  запущенную сцену камерой редактора — вращение, полёт по W/A/S/D, выбор, гизмо, меню, клавиши редактора;
  ввод игры отключён. Снятие паузы возвращает вид Game (если он был выбран).
- **Ввод:** у `Game` есть `input` (`Input`), поведения читают его как `self.input`. В редакторе канвас
  подключается к нему (`input.attach`) только в виде Game (`sceneStore.gameInput`); в виде Scene клавиши и
  мышь принадлежат редактору. В виде Game горячие клавиши редактора, кроме Ctrl+P и Ctrl+S, отключены.
  Нажатия в текстовых полях до игры не доходят.
- **Stop** (`requestStop`): если сцена изменилась с момента Play (сравнение с JSON-снимком `playSnapshot`),
  спрашивает Keep / Discard / Continue playing. `stop(true)` оставляет правки, `stop()` возвращает снимок.
  Автоматические остановки (загрузка сцены, вход в префаб) правки отбрасывают. Сохранение сцены и
  Create Prefab во время Play запрещены: правки ещё могут быть отброшены. Правка скрипта, материала или
  префаба на диске перезапускает Play.
- **Look** — ассет `looks/<имя>.json`: `pixelSize`, `toneMapping`, `exposure`, списки `surfaces` и `effects` и
  необязательный `extends` (стиль построен на другом). Сцена ссылается на него полем `environment.look`.
  Эффект — `defineEffect({ name, params, inputs, shader })`: кусок GLSL, определяющий
  `effect(uv, color)`; параметры становятся uniform'ами с теми же именами. Встроенные (`outline`,
  `palette`, `grade`, `vignette`) написаны этим же способом и зарегистрированы в каждом `Registry`;
  эффекты проекта приходят из `scripts/` через `registerExports`. `RenderPipeline` рисует сцену в
  полуплавающие текстуры (линейный цвет), при надобности — второй раз с материалом нормалей, прогоняет
  эффекты по очереди и выводит на канвас с переводом в sRGB. Без Look (или с пустым) это обычный
  `renderer.render`. Шейдеры пересобираются только при смене списка эффектов, числа меняются на лету.
  В редакторе: вкладка Looks в Project, `LookInspector` (унаследованные эффекты помечены, их правка
  пишется в этот Look, базовый не трогается). Во вьюпорте — список выбора Look сцены и кнопка-глаз
  (`sceneStore.lookEnabled`), которая выключает Look только для вьюпорта. «Standard (no effects)» в списке —
  сцена без Look, обычный рендер three.js.
- **Поверхность** (`surfaces` в Look) — добавка к материалам всей сцены: то, чего нельзя сделать с готовой
  картинкой. `defineSurface({ name, params, defines, vertex, fragment })`: `vertex` определяет
  `surfaceVertex(clip)` (место вершины на экране), `fragment` — `surfaceColor(color, albedo)` (освещённый
  цвет), `defines` включает переключатели шейдеров three.js. Встроенные: `vertexSnap` (дрожание вершин PS1),
  `toon` (свет полосами), `flat` (плоские грани). Материалы никто не регистрирует: `Surfaces.prepare` перед
  каждой картинкой обходит видимые меши сцены и ставит материалам `onBeforeCompile` — так охвачены и
  материалы проекта, и те, что создают модели из кода; у материала без шейдерных кусков three.js (свой
  `ShaderMaterial`) ничего не меняется. Все поверхности стиля попадают в один шейдер, их параметры и
  функции разведены по именам через `#define`. Uniform'ы общие на все материалы: числа меняются на лету,
  шейдеры пересобираются только при смене списка. Без стиля (или с выключенным глазом) `restore` возвращает
  материалам исходный вид. Материал нормалей для контуров получает те же `vertex` и `defines`.
- **Инструменты редактора рисуются после Look** и эффектами не задеваются. Сетка и маркеры света и камеры
  лежат на слое three.js `EDITOR_LAYER` (1): вьюпорт рисует картинку камерой со слоем 0, затем на канвасе
  заново пишет глубину сцены (материал без записи цвета) и поверх — слой редактора, так что объекты его
  заслоняют. Гизмо остаётся на слое 0 (иначе его не ловит луч `TransformControls`), прячется на время
  картинки и рисуется последним. У сцены с цветным фоном three.js очищает канвас при каждом `render`,
  поэтому на эти проходы `scene.background` снимается.
- **Build:** `buildGame` собирает Vite'ом один файл `game.js` (формат IIFE, обычный `<script>`): движок,
  three.js, все скрипты проекта, материалы и префабы, одна стартовая сцена — и вызывает `runGame`. Рядом
  пишется `index.html`, папка `assets/` копируется как есть. Результат — `projects/<имя>/build/` (в
  `.gitignore`), открывается с диска без сервера. Точка входа — виртуальный модуль, временных файлов нет.
  В редакторе кнопка Build (собирает с открытой сцены; несохранённая сцена — отказ) и ссылка Open game на
  `/__game/<имя>/`, где dev-сервер раздаёт сборку как есть. Папки `build` исключены из слежения Vite.
- **Префаб** — `prefabs/<имя>.json` с `root`. Экземпляр в сцене — объект с полем `prefab` и своим
  transform; содержимое берётся из файла. Объекты внутри экземпляра не имеют `entityId`, поэтому клик
  во вьюпорте выбирает экземпляр целиком.
- **Переопределения** — поле `overrides` экземпляра: `{ "<путь из имён от корня префаба>": { active,
  position, rotation, scale, components: { "<ключ компонента>": { поля } } } }`, `"."` — корень. Менять
  можно только существующее (добавить, убрать, переименовать — в самом префабе). `expandInstance` даёт
  экземпляр как обычный объект: содержимое префаба плюс переопределения; так его строит `createEntityObject`,
  так же его видят `Runtime` и валидация. Объекты внутри получают id `"<id экземпляра>/<путь>"` (на three.js-
  объекте — `userData.innerId`), по ним их знают `sceneStore.objects` и `Game.objects`, поэтому гизмо и
  правка в Play работают как с обычными. Путь, уходящий во вложенный экземпляр другого префаба, переносится
  в его собственные `overrides`. В редакторе: экземпляр в Hierarchy раскрывается (по умолчанию свёрнут), его
  внутренности — курсивом, изменённые — жирным; их можно выбрать и править в Inspector или гизмо. Методы
  store не пишут переопределения сами: `locate(id)` даёт копию объекта с применёнными переопределениями,
  метод правит её как обычный объект, `commit` сравнивает с префабом (`diffOverride`) и записывает разницу в
  экземпляр — вернул значение как в префабе, переопределение исчезло. Компоненты самого экземпляра
  (корня префаба) правятся так же (`locate(id, true)`). Revert — `revertOverrides(id)`. Unpack сохраняет
  переопределения в получившихся объектах. Изменённые поля в Inspector помечены (синяя жирная подпись,
  `sceneStore.overrideOf(id)`); правый щелчок по такой подписи — Revert to Prefab для одного поля
  (`revertOverrideField`). Apply (`applyOverrides(id)` в `actions.ts`, кнопки в Inspector и пункты
  контекстного меню) вписывает переопределения в префаб (`applyToPrefab`), сразу пишет файл префаба и
  убирает их из экземпляра: для экземпляра — все, для объекта внутри — только его. Во время Play и для
  префаба, открытого на редактирование, Apply недоступен. Режим редактирования префаба показывает его отдельной сценой, сцена
  ждёт в `stash`; выход сохраняет префаб.
- **Undo / redo** (`sceneStore.undo()` / `redo()`, кнопки в Toolbar, Ctrl+Z, Ctrl+Y или Ctrl+Shift+Z) — снимками:
  любая правка данных сцены кончается в `notify()`, там `record()` сравнивает JSON сцены с прошлым и кладёт
  прошлый в стек (до 100 шагов). Новым методам store ничего делать не надо. Правки, идущие чаще чем раз в
  400 мс (перетаскивание гизмо, набор числа), сливаются в один шаг. Откат заменяет данные и пересобирает
  объекты (`restore`, тот же код, что у Stop без Keep); во время Play перезапускает копию. Загрузка сцены
  (в том числе перезагрузка с диска после внешней правки) историю сбрасывает; у префаба своя история, история
  сцены ждёт в `stash`. Отброс правок при Stop — тоже шаг, его можно отменить. Выделение в историю не входит.
  В том же стеке лежат шаги ассетов — правка, создание и удаление материала или Look: их записывает
  действие в `actions.ts` (`sceneStore.recordAsset(section, name, before, after)`, `null` — ассета нет), а
  откат выполняет `sceneStore.assetHandler` (реестр и файл на диске). Шаги сцены и ассетов отменяются в том
  порядке, в каком были сделаны; сливаются только соседние правки одного и того же.
- **Вид из камеры:** пока выбран объект с компонентом `camera` (и нет Play), вьюпорт рисует в правом нижнем
  углу то, что видит эта камера (`sceneStore.previewCamera`): тем же `RenderPipeline` и с тем же Look, в
  области канваса, заданной `setViewport` / `setScissor`. Рамка и имя — элемент `.viewport-preview` поверх.
- **Внешние правки:** сервер шлёт `white:asset-changed` для JSON-файлов, изменённых не через API.
  Сцену без несохранённых правок редактор перезагружает сам, иначе пишет об этом в строке статуса.
- **Объекты редактора** (гизмо, сетка, маркеры света и камеры, свет режима префаба) живут вне
  `sceneStore.root` или помечены `userData.editorHelper` и в файлы не попадают.

## Управление

- Левая кнопка: клик — выбор, перетаскивание — вращение камеры. Средняя (или Shift + левая) — сдвиг,
  колесо — приближение.
- Зажатая правая кнопка: осмотр мышью, W/A/S/D — полёт, Q/E — вниз/вверх, Shift — быстрее.
- Щелчок правой кнопкой — контекстное меню (Hierarchy и вьюпорт).
- Без правой кнопки: W/E/R — перемещение/поворот/масштаб, F или двойной клик в Hierarchy — фокус,
  Del — удалить, Ctrl+D — дублировать, Ctrl+S — сохранить, Ctrl+Z / Ctrl+Y — отменить / вернуть,
  Esc — снять выделение.
- Play: Ctrl+P — запуск / стоп, Ctrl+Shift+P — пауза, Ctrl+Alt+P — шаг на кадр. В виде Game клавиши и мышь
  идут в игру; на паузе и в виде Scene действует всё управление редактора.

## Что не сделано и не проверено

- Перетаскивание (Hierarchy, Project → сцена, объект → Project) проверено только программными событиями.
- Полёт камеры и клавиши проверены программными событиями, не настоящими мышью и клавиатурой.
- Стартовый экран (`Welcome`), Save As, Del, Ctrl+D, вложенные префабы — написаны, вживую не проверялись.
- Переопределения в экземплярах: нельзя добавить или убрать объект или компонент, переименовать. Apply пишет файл префаба сразу и в undo не
  входит (undo вернёт переопределение экземпляру, префаб останется изменённым — картинка та же). Другие
  экземпляры со своим переопределением того же поля его сохраняют. Объекты адресуются именами: одинаковые имена соседей в префабе и `/` в имени не поддержаны, после
  переименования в префабе переопределение «повисает» (`check` это ловит, редактор молча пропускает).
  Проверено программно (методы store, Play, undo, revert, unpack, Apply нажатием кнопок, `check` на ошибочном
  файле) и снимком Inspector с пометками; настоящей мышью, гизмо на внутреннем объекте и вложенные префабы
  не проверялись.
- Play проверен программно (нажатие кнопок и шаги `tick` из консоли) и снимком экрана, глазами движение
  во вьюпорте не смотрели.
- Ввод проверен программными событиями клавиш и настоящим кликом мыши; настоящая клавиатура в идущей
  игре не проверена. Нет захвата указателя (pointer lock), геймпада и касаний.
- Поведения: нет доступа к другим поведениям, нет `destroy`. Объекты,
  добавленные во время Play (в том числе через `instantiatePrefab` из поведения), свои скрипты не запускают.
- Поведения не показаны в панели Project.
- Поверхности: «плывущих» текстур PS1 нет (в материалах нет текстур). Тени и проход глубины для сетки и
  маркеров рисуются без сдвига вершин — при `sway` или крупном `vertexSnap` сетка и тени расходятся с
  объектами. `toon` считает свет по готовому цвету (яркость / яркость материала), а не по каждому источнику;
  `range` подбирается под свет сцены руками. Проверено в редакторе снимками экрана (PS1, toon + flat + контур,
  `sway`, смена чисел после выключения и включения стиля); в Play и в собранной игре не смотрели. Кнопки
  списка Surfaces в Inspector (добавить, убрать, переставить) мышью не нажимались. При движении камеры пиксели
  «кипят»: нет ортографической камеры и привязки к пиксельной сетке. Край заслонения сетки и маркеров чёткий, а силуэты в картинке
  крупнопиксельные — на стыке возможен зазор до размера пикселя. Ошибки шейдеров видны только в консоли браузера. Перестановка эффектов, добавление из
  меню и перетаскивание Look в сцену мышью не проверялись. Камера для эффектов глубины — только перспективная.
- Build: в сборке одна сцена, перехода между сценами нет; проект перед сборкой не проверяется; открытие
  `index.html` с диска (без сервера) и копирование `assets/` не проверялись.
- В `tsconfig.node.json` добавлена библиотека `DOM`: `tools/` импортирует движок, а в нём есть код браузера.
- Dev-сервер иногда отдаёт устаревший модуль после нескольких быстрых правок одного файла подряд —
  помогает пересохранить файл.
- Материалы нельзя переименовать, в них нет текстур.
- Вид из выбранной камеры: размер фиксированный (30 % вьюпорта), пропорции — как у вьюпорта, а не у будущего
  окна игры; при Look с `pixelSize` картинка уменьшена после пикселизации и может рябить. Проверено снимком.
- Скрытие полей по `when` проверено на свете (программно); у параметров моделей и поведений не проверялось.
- Панель Project — плоские списки по типам, без дерева папок и без контекстного меню.
- Undo / redo покрывает сцену, редактируемый префаб, материалы и Look (правка, создание, удаление). Не входят:
  создание и удаление сцен и префабов, Create Prefab и Apply (файл префаба остаётся), правки файлов извне.
  Шаги ассетов лежат в истории открытой сцены: загрузка другой сцены их сбрасывает, а на время правки
  префаба они ждут вместе с историей сцены. В текстовом поле Ctrl+Z —
  отмена браузера в этом поле, а не шаг редактора. Проверено программно (методы store и действия, события клавиш,
  нажатие кнопок; для ассетов — что файлы на диске после откатов совпали с исходными); настоящей клавиатурой
  и в режиме префаба не проверялось.
- В зависимостях остались неиспользуемые `zustand`, `tailwindcss`, `@tailwindcss/vite`; `README.md` —
  от шаблона Vite. `npm audit` сообщал об уязвимостях в зависимостях, их не трогали.

## План дальше

Направление автора (октябрь 2026): игры в примитивной графике с сильной стилизацией — пиксель-арт в 3D
с контурами и ограниченной палитрой, стиль PS1, позже, возможно, чёткая картинка «под реализм» со светом.

новый эффект — файл в `scripts/`, новый стиль — файл в `looks/`.
